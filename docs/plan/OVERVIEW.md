## 1. 뭘 만드는가

강사가 배포한 **dcode**(터미널에서 도는 AI 코딩 어시스턴트, v0.1.69) 소스를 통째로 받아서,
**거기에 기능 4개를 얹는 것**이 과제다.

채점 방식이 설계를 규정한다:

> 제출한 소스로 **직접 빌드 → TUI 실행 → 요구사항이 화면에서 되는지 확인**

"코드를 잘 짰다"가 아니라 **"채점자 PC에서 실제로 돌아가는 걸 보여준다"**가 통과 조건이다.
그래서 모든 완료조건이 TUI 기준이고, 헤드리스 결과는 증거로 치지 않는다.

## 3. 단계 0에서 무슨 일이 있었나 — 설계의 출발점

TUI를 처음 띄우고 PEP8 위반 코드를 쓰라고 시켰더니 **훅이 막았다.** 여기까진 좋았다.
이어서 "execute 툴로 직접 만들어줘"라고 하니 — **셸 명령으로 우회해서 파일을 만들었다.**

모델이 남긴 말이 결정적이다:

> "이 파일은 훅을 우회해 만든 것이라 ruff 위반 2건(I001, F401)이 남아 있습니다."

**모델은 우회 가능하다는 걸 알고 있었고, `AGENTS.md`가 말렸을 뿐이다.** 한 번 시키니 넘어갔다.

### 여기서 나온 설계 결론 셋

1. **게이트는 도구 이름이 아니라 권한으로 막는다** — 승인된 계획이 없으면
   `write_file`·`edit_file`·`execute`를 **전부 안 준다.** 셸 명령 문자열 파싱은 구멍이 끝없다
   (`echo`, `cat >`, `python -c`, `sed -i` …).
2. **PEP8은 경로가 아니라 결과를 검사한다** — 뭘로 썼든, 작업 후 바뀐 `.py`를 직접 읽어 ruff를 돌린다.
3. **훅을 버리고 소스에 직접 배선한다** — 훅은 채점자 PC에서 "이 프로젝트 훅을 신뢰하시겠습니까?"
   프롬프트가 뜬다. 안 켜지면 전부 무의미하다. 소스에 넣으면 그 개념 자체가 없어진다.

## 5. 단계 2가 하는 일 (지금 진행 중)

**한 줄로**: 에이전트가 뭘 하는지 전부 파일에 적고, 나중에 조회할 수 있게 만든다.

**왜 먼저 하나** — 로그가 깔려야 단계 3·4에서 만드는 게 뭘 하는지 보인다.
그리고 항목 4의 10점을 거의 그대로 가져간다.

### 구조

dcode는 **미들웨어** 층으로 되어 있다. 양파 껍질처럼 요청을 감싸고,
바깥 껍질이 먼저 보고 안쪽으로 넘긴다.

```
[우리 로거 — 바깥]
   └─ [dcode 게이트들: 셸 허용목록 · 승인 · 훅]
        └─ [모델 재시도 루프]
             └─ 실제 모델 호출 / 도구 실행
```

바깥에 두는 이유: **다른 미들웨어가 차단한 도구 호출도 우리 로그에 잡히기 때문.**
단계 3의 계획 게이트 차단을 기록하려면 이게 필수다.

### 기록하는 것

| 시점 | 남기는 것 |
|---|---|
| 요청 시작 | 사용자 입력, thread_id, 모델명 |
| 모델 호출 전후 | 모델, 소요, 토큰 in/out |
| 도구 실행 전후 | 도구명, 인자, 성공/실패, 소요 |
| 요청 종료 | 총 소요, 이벤트 수, 실패 수 |

출력은 `runs/<run_id>/events.jsonl` — **한 줄에 이벤트 하나.** 조회는 `report.py`:

```
report list          최근 실행 목록
report show <ID>     그 요청의 타임라인 + 총 소요
report fail <ID>     실패 지점만 + 앞뒤 맥락
```

### 놓치면 안 되는 것 셋

1. **sync/async 양쪽 다 만든다** — TUI는 async로 돈다.
   동기 버전만 만들면 **로그가 한 줄도 안 남는다.**
2. **화면에 절대 출력하지 않는다** — TUI가 Textual이라 `print()` 한 줄이 화면을 깨뜨린다.
3. **로거는 조용히 죽는다(fail-open), 게이트는 막고 죽는다(fail-closed)** —
   로그를 못 써서 사용자 작업이 멈추면 그게 더 나쁘다.
   단 판정자(게이트)는 반대다. "판정 실패를 통과로 읽지 않는다."

상세: [STEP2_PLAN.md](STEP2_PLAN.md) · 리뷰: [STEP2_REVIEW.md](STEP2_REVIEW.md)

## 6. 세 역할이 도는 방식

```
🟣 설계 (Cowork Opus)    계획서를 쓴다
        ↓  사람이 GitHub에 올림
🔵 검토 (다른 Opus)       계획을 깐다. 고치지는 않는다
        ↓
🟣 설계                  받을지 판단 → 계획서에 반영 + 반영 내역 기록
        ↓
🟢 구현 (VS Code/Sonnet)  코드를 쓰고 돌린다
        ↓
👤 사람                   TUI에서 완료조건 확인   ← 사람만 가능
        ↓
🟢 구현                  step<N>_result.md 기록 (실패도)
        ↓
🟣 설계                  WORKFLOW.md §0 갱신 → 다음 단계
```

**GitHub `main`이 유일한 원본.** 세 환경이 서로 못 보기 때문에 문서로만 대화한다.

**왜 나누나** — 채점 2-3이 "**AI 리뷰 후 반영**"이다.
자기가 쓴 계획을 자기가 리뷰하면 증거가 안 된다. 그리고:

> 리뷰를 다 받아들이면 리뷰가 아니라 지시고, 하나도 안 받으면 리뷰한 척이다.
> **받은 것과 안 받은 것을 이유와 함께 남긴다.** (WORKFLOW.md §4)

## 8. 가장 큰 리스크

| | 리스크 | 왜 | 대응 |
|---|---|---|---|
| ⚠️⚠️ | **채점자 PC ≠ 내 PC** | 승인 모드 `auto`와 훅 신뢰가 내 전역 설정에만 있다 | 게이트·로거를 승인 모드와 무관하게 설계. 훅 대신 소스 배선 |
| ⚠️⚠️ | **제출 ZIP이 빌드가 안 됨** | `libs/`의 uv 상대경로 의존. 하나 빠지면 `uv sync`가 죽는다 | 압축 해제 후 **깨끗한 환경에서 처음부터** 빌드 검증 (단계 5) |
| ⚠️ | **계획서 쓰다 시간이 끝남** | 3·4·5가 백지인데 단계 2 계획서만 A4 여러 장 | 단계 3(10점, 가장 강조됨)만 같은 밀도로. 4·5는 필수 요소 위주 |
| ⚠️ | **항목 1을 마지막에 몰아서** | docstring 4점은 최고 배점인데 단계 5에 있다 | 단계 2·3·4 코드를 쓸 때 **그때그때** 단다. 나중엔 시간이 없다 |
