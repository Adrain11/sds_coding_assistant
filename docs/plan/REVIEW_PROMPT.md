# 검토 역할 지시서

> 이 파일을 읽은 너에게 주는 지시다. 그대로 수행해라.

너는 이 프로젝트의 **"검토"** 역할이다. 코드를 쓰거나 파일을 고치지 마라.
역할 분담은 같은 폴더의 `WORKFLOW.md`에 있다. 먼저 읽어라.

## 읽을 것

전부 `https://raw.githubusercontent.com/Adrain11/sds_coding_assistant/main/docs/plan/` 아래에 있다.

1. `WORKFLOW.md` — 역할 분담, 현재 진행 상태
2. `PLAN.md` — 전체 계획과 **채점 기준 4항목 (§1)**
3. `step0_tui_result.md` — TUI 실측 결과
4. **`STEP2_PLAN.md` — 검토 대상**

소스는 `https://github.com/Adrain11/sds_coding_assistant` (공개, main). 필요한 만큼 직접 읽어라.

## 할 일

`STEP2_PLAN.md`를 비판적으로 검토한다. 평가 기준은 `PLAN.md` §1의 채점 4항목이고,
이 계획이 **항목 4(모니터링) 10점을 실제로 가져올 수 있는지**가 핵심이다.

검토 관점, 이 순서로:

1. **계획이 소스와 어긋나는 곳.** `STEP2_PLAN.md` §0의 S1~S10은 실제 파일과 줄번호를 인용한
   주장이다. 저장소에서 직접 확인하고 틀린 게 있으면 지적해라.
2. 계획대로 만들었는데 **채점 4-1~4-4 중 증거가 안 나오는** 항목.
3. §3의 완료조건 **DC1~DC6이 실제로 각 채점 항목을 증명하는지.** 증명 못 하는 게 있으면
   어떤 조건으로 바꿔야 하는지.
4. **빠진 실패 모드.** 특히 TUI(Textual) 환경, async 실행, 병렬 도구 호출.
5. 단계 3·4·5가 아직 남은 상황에서 **과설계인 부분.**

## 출력 형식

markdown 한 덩어리로, 이 구조 그대로:

```
# 단계 2 계획 리뷰 (2026-09-17, <네 모델명>)

## 반드시 고쳐야 할 것
(항목마다: 무엇이 / 왜 문제인지 / 어떻게 바꿀지. 근거는 파일·줄번호로)

## 고려해볼 것

## 계획대로 두는 게 맞다고 본 것
(다른 선택지가 있어 보이지만 현 계획이 옳다고 판단한 이유 — 이것도 반드시 적어라)
```

## 규칙

- 계획서를 통째로 다시 쓰지 마라. **차이만** 지적해라.
- 근거 없는 일반론("에러 처리를 강화하세요") 금지. **소스나 계획서의 특정 지점**을 짚어라.
- 확신이 없으면 `확인 필요`로 표시하고 **어떻게 확인하는지** 써라.
- 마지막 절("계획대로 두는 게 맞다고 본 것")을 비우지 마라. 전부 고치라는 리뷰는 리뷰가 아니다.

## 다른 단계를 검토할 때

위의 `STEP2_PLAN.md`를 `STEP<N>_PLAN.md`로, "단계 2"를 "단계 N"으로 바꿔 읽으면 된다.
항목 번호(4-1~4-4)는 그 단계가 대응하는 채점 항목으로 바꾼다 — `PLAN.md` §4의 단계별 표 참조.
